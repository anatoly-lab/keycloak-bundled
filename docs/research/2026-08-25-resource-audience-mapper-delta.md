# Resource→audience mapper: 26.7.2 deltas

Date: 2026-08-25 · Baseline: `mcpwarp/docs/research/2026-08-25-keycloak-resource-audience-spi.md` (verified against 26.7.0)
Source of truth: shallow clone of `github.com/keycloak/keycloak` tag `26.7.2` (commit `289376b142480b4d600aca7acb1e4651862ed2a1`). All `file:line` below are relative to that tree.

## Summary

### REFUTED — "/token does not parse `resource`"
26.7.2 parses the `resource` form param on **every** token-endpoint grant and exposes it as a `ClientSessionContext` attribute:
- `services/.../protocol/oidc/grants/OAuth2GrantTypeBase.java:116` — `clientSessionCtx.setAttribute(OAuth2Constants.RESOURCE, formParams.getFirst(OAuth2Constants.RESOURCE))` (runs for code, client-credentials, device, CIBA — everything extending `OAuth2GrantTypeBase`). Line 115 also sets `Constants.GRANT_TYPE`.
- `services/.../grants/RefreshTokenGrantType.java:65,82` — reads `resource` and passes it into `RefreshTokenContext`.
- `services/.../protocol/oidc/refresh/AbstractRefreshTokenProvider.java:150` — `validation.clientSessionCtx.setAttribute(OAuth2Constants.RESOURCE, ctx.resourceParameter())`.
- `services/.../grants/ResourceOwnerPasswordCredentialsGrantType.java:140` — same.

A custom mapper can therefore read **either** source: `clientSessionCtx.getAttribute(OAuth2Constants.RESOURCE, String.class)` (this request's `resource`) or the client-session note (the `/authorize`-time one). Note: the attribute is set to `null` when the param is absent, so it is not a fallback for the note.

### CONFIRMED — constant, note key, storage site
- `OIDCLoginProtocol.RESOURCE_PARAM = OAuth2Constants.RESOURCE` — `services/.../protocol/oidc/OIDCLoginProtocol.java:90`; value `"resource"` — `core/.../OAuth2Constants.java:133`. **The note key stored is the literal string `resource`** (no prefix).
- `/authorize` stores it as an auth-session **client note**: `services/.../endpoints/AuthorizationEndpoint.java:350` (`performActionOnParameters(request, (n,v) -> { if (v != null) authenticationSession.setClientNote(n, v); })`), with `RESOURCE_PARAM` in the param set at `:470`. Parsed/known param at `AuthzEndpointRequestParser.java:83,137`.
- Copied verbatim to the persisted `AuthenticatedClientSessionModel` at code exchange: `services/.../protocol/oidc/TokenManager.java:473-476` (`authSession.getClientNotes()` → `clientSession.setNote(k,v)` for every note).

### CONFIRMED — note survives refresh, and `transformAccessToken` sees it
Refresh path: `RefreshTokenGrantType.process` → `RefreshTokenProvider.refreshAccessToken` → `AbstractRefreshTokenProvider.refreshAccessToken`:
- `AbstractRefreshTokenProvider.java:121` — `tokenManager.createClientAccessToken(session, realm, client, user, userSession, clientSessionCtx, ...)`, where `clientSessionCtx` is `validation.clientSessionCtx`, built from the **persisted** `AuthenticatedClientSessionModel` (`:124` `validation.clientSessionCtx.getClientSession()`).
- `TokenManager.java:426-429` — `createClientAccessToken` calls `transformAccessToken(...)`.
- `TokenManager.java:824-830` — iterates `ProtocolMapperUtils.getSortedProtocolMappers(session, clientSessionCtx, m -> m.getValue() instanceof OIDCAccessTokenMapper)` and calls `((OIDCAccessTokenMapper) m).transformAccessToken(token, model, session, userSession, clientSessionCtx)`.

So on refresh the mapper gets a `ClientSessionContext` whose `getClientSession().getNote("resource")` is the value captured at `/authorize`. Baseline claim holds.

### NEW — RFC 8707 support (PR #46763) **is already shipped in 26.7.2**, experimental
Baseline said "expected 26.8/27". It is in 26.7.2, behind a flag.
- Feature: `common/.../Profile.java:199` — `RESOURCE_INDICATORS("Resource Indicators for OAuth 2.0", Type.EXPERIMENTAL)`. **EXPERIMENTAL ⇒ off by default.** CLI key derived at `Profile.java:241` (`name().toLowerCase().replace('_','-')`) ⇒ `--features=resource-indicators`.
- Factory gate: `services/.../protocol/oidc/resourceindicators/ResourceIndicatorsPostProcessorFactory.java:12,26` — provider id `resource-indicators`, `EnvironmentDependentProviderFactory.isSupported` → `Profile.isFeatureEnabled(RESOURCE_INDICATORS)`. Registered under SPI `token-post-processor` (`TokenPostProcessorFactory`).
- What it does (`ResourceIndicatorsPostProcessor.java:21-68`): validates the requested `resource`; for `authorization_code` compares against `code.getResource()`, for `refresh_token` against the `resource` claim it stamps into the refresh token (`:66`); then resolves an audience and calls `context.accessToken().audience(audienceToSet)` — **`audience(...)`, which REPLACES the whole `aud` array**, not `addAudience`.
- Resolution is restricted (`:56-90`): either `urn:client:<clientId>` matched against an audience **already present** in the token, or a plain URL matched against a client's `resource_url` attribute (`ResourceIndicatorConstants.java:7`) for a client already in `aud`. It cannot mint an audience that isn't already there. **Unusable for thousands of dynamic per-server URLs** — each would need its own Keycloak client carrying `resource_url`. Baseline's conclusion (build a custom mapper) stands.
- **Not feature-gated:** `/authorize` now always syntax-validates `resource` — `AuthorizationEndpoint.java:192` → `AuthorizationEndpointChecker.java:288-296` → `ResourceIndicatorValidation.isValidResourceIndicator` (`ResourceIndicatorValidation.java:14-38`): must be an absolute URI, **no fragment, no query, non-null path**; URNs matched against a regex. `https://<id>.mcpwarp.io/mcp` passes. A malformed value ⇒ 400 `invalid_target` before any mapper runs.
- Interaction risk: if anyone ever enables `resource-indicators` alongside a custom mapper, the post-processor's `audience(...)` runs and would clobber the mapper's `aud`. Keep the feature off.

### CONFIRMED — `AbstractOIDCProtocolMapper` contract in 26.7.2
- Base class and all mapper interfaces live in the **`services`** module, not `server-spi-private`: `services/src/main/java/org/keycloak/protocol/oidc/mappers/`. ⇒ the plugin pom needs `org.keycloak:keycloak-services` at `provided` scope (managed by `keycloak-parent`, root `pom.xml:1082-1086`).
- Implement: `AbstractOIDCProtocolMapper` + `OIDCAccessTokenMapper` (`OIDCAccessTokenMapper.java` — single method `transformAccessToken`). Add `TokenIntrospectionTokenMapper` if introspection should show the audience. **Do not** add `OIDCIDTokenMapper` or `UserInfoTokenMapper` for an audience — the built-in `AudienceProtocolMapper` implements `OIDCAccessTokenMapper, OIDCIDTokenMapper, TokenIntrospectionTokenMapper` but defaults ID-token inclusion to `false` (`AudienceProtocolMapper.java:36,67-72`).
- Override `setClaim(IDToken token, ProtocolMapperModel, UserSessionModel, KeycloakSession, ClientSessionContext)` (`AbstractOIDCProtocolMapper.java:156`). The base `transformAccessToken` (`:89-99`) gates on `access.token.claim` (or `lightweight.claim` when lightweight tokens are on) before calling `setClaim`.
- **Append without clobbering:** `token.addAudience(String)` — `core/.../representations/JsonWebToken.java:216-231`, appends and de-duplicates. `audience(String...)` at `:211` **replaces**. `AudienceProtocolMapper.java:112` uses `addAudience`. Use `addAudience`; never `setOtherClaims("aud", ...)` — `aud` is a typed field (`JsonWebToken.java:63`), an `otherClaims` entry would collide/serialize wrong.
- `ProviderConfigProperty` types (`server-spi/.../provider/ProviderConfigProperty.java`): `BOOLEAN_TYPE="boolean"` (:30), `STRING_TYPE="String"` (:42), `TEXT_TYPE="Text"` (:75, multi-line textarea — use for a newline-separated allowlist), `MULTIVALUED_STRING_TYPE="MultivaluedString"` (:47, repeatable list), `LIST_TYPE`/`MULTIVALUED_LIST_TYPE` (:57,:62, fixed options), `CLIENT_LIST_TYPE` (:64), `MAP_TYPE` (:80). Note `MULTIVALUED_STRING_TYPE` values are stored joined by `##` in the mapper config.
- Registration: `META-INF/services/org.keycloak.protocol.ProtocolMapper` (matches Keycloak's own `services/src/main/resources/META-INF/services/org.keycloak.protocol.ProtocolMapper`). `ProtocolMapper extends Provider, ProviderFactory<ProtocolMapper>, ConfiguredProvider` (`server-spi-private/.../protocol/ProtocolMapper.java:32`), so one class is both provider and factory; `getId()` is the provider id, plus `getDisplayCategory()`, `getDisplayType()`, `getHelpText()`, `getConfigProperties()`, `getProtocol()` (given by the base class).
- **Per-mapper disable spelling:** the SPI name is `protocol-mapper` (`ProtocolMapperSpi.java:36`) and the generic per-factory kill switch is `scope.getBoolean("enabled", true)` in `services/.../DefaultKeycloakSessionFactory.java:336-338`. Current (26.x) option format uses a **double dash** between spi / provider / option: `--spi-protocol-mapper--<provider-id>--enabled=false`. The legacy single-dash `--spi-protocol-mapper-<provider-id>-enabled=false` is still accepted — `quarkus/runtime/.../mappers/PropertyMappers.java:100-105` keeps the non-strict form ("we can't require the new property format until we're ok with a breaking change"). Use the double-dash form; it is a **build-time** option (`isSpiBuildTimeProperty`), so it must be passed to `kc.sh build`, not just to `start`.

### CONFIRMED (with a caveat) — DCR and realm DEFAULT client scopes
Realm default scopes ARE attached to DCR-created clients:
- `model/jpa/.../ClientAdapter.java:274-279` — `setProtocol` publishes `ClientProtocolUpdatedEvent`.
- `server-spi-private/.../protocol/AbstractLoginProtocolFactory.java:47-56` — listener on that event calls `addDefaultClientScopes(client.getRealm(), client)`, which at `:81-97` adds `realm.getDefaultClientScopesStream(true)` (filtered to the matching protocol) as default and `(false)` as optional.
- DCR path: `OIDCClientRegistrationProvider.createOIDC` → `DescriptionConverter.toInternal` (sets `protocol = openid-connect`, `DescriptionConverter.java:85`) → `AbstractClientRegistrationProvider.java:86` → `ClientManager.createClient:85` → `RepresentationToModel.createClient` → `updateClientProperties` sets the protocol ⇒ event fires ⇒ realm defaults attached.

**Caveat (verify before relying on it):** `RepresentationToModel.createClient:411` then calls `updateClientScopes` (`:663-689`), which — when the rep has `defaultClientScopes` **or** `optionalClientScopes` non-null — **removes every existing scope not in the requested set**, including the realm defaults just attached (`:675-679`). `DescriptionConverter.toInternal:87-91` sets `optionalClientScopes` whenever the DCR request carries a `scope` field. So a client registering with `scope=openid profile ...` can have the realm-default scope stripped from its defaults. Mitigations: rely on the client requesting the scope explicitly (it lands as *optional*, then needs to be requested per-authorization), or attach the mapper to a scope the client always sends, or add the mapper directly to the client via the registration policy. Needs an empirical check against a real DCR request.
- DCR "Allowed Client Scopes" policy: `services/.../clientregistration/policy/impl/ClientScopesClientRegistrationPolicy.java:55-66` checks only the **requested** scope names; `getAllowedScopeNames:123-134` includes all realm default+optional scopes when `allow-default-scopes` is true (default true, `:129`).

## Open questions
1. The `updateClientScopes` strip-on-DCR behaviour above — confirm empirically with a `POST /clients-registrations/openid-connect` carrying a `scope` field, against 26.7.2.
2. Which source should the mapper prefer when both exist: the `/authorize`-time client note vs. the per-request `ClientSessionContext` attribute? Reading the note is the conservative choice (client cannot escalate audience at `/token`); reading the attribute would allow per-token narrowing but needs its own validation. Baseline says exactly one resource per token — decide and document.
3. Refresh with a *different* `resource` than the original: with the custom-mapper approach nothing compares them (the built-in post-processor does, but it is off). If per-request narrowing is allowed, the mapper must implement the comparison itself.
4. Should the mapper also implement `TokenIntrospectionTokenMapper` so the tunnel's introspection view matches the token? (Not needed if the tunnel does local JWT verification only.)
5. `aud` clobber risk: `AudienceResolveProtocolMapper` (the built-in `roles` scope mapper) also writes `aud`. Mapper ordering is by `ProtocolMapper.getPriority()` — since we use `addAudience` this is additive, but verify no other mapper in the realm calls `audience(...)`.

If the JAR is renamed to something generic, the Dockerfile `test -f`/`COPY` and pom `<finalName>` must change together.
